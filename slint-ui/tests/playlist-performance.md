# 歌单滚动与封面更新性能记录

## 2026-11-09：已登录真实歌单与缓存

用重构版保存的会话调用实际 `user_account`、`user_playlist` 和 `playlist_detail`，定位「主歌单」。详情实际返回 455 首曲目、367 个不同封面 URL，单次详情请求约 2.34 秒，已经包含全部歌曲，因此这次没有 `song_detail` 补全请求。用户原有磁盘缓存命中 188 张 128px 缩略图，另 179 张未命中。测试只读取账号，运行时使用配置和缓存的独立副本；凭据及 API 原始响应不进入仓库或日志。

之前模拟歌曲预加载封面的测试漏掉了两条路径：

- Slint 1.18.1 的普通 `VecModel` 为所有按索引读取的行共享同一个变更依赖。一张图片到达后，虽然 Rust 仅更新匹配行，整个可见列表的绑定仍然失效，下一轮输入重新计算文字和布局。
- 图片内存缓存的 256 张数量上限只能容纳约 16 MiB 的 128px 缩略图，远未达到 64 MiB 字节上限。这份歌单有 367 张不同封面，回滚时发生反复淘汰和解码；磁盘缓存命中无法消除这些开销。

现在 `CoverModel` 给按索引读取的行分别建立通知依赖，普通 repeater 保留逐行通知。首页、歌曲列表、侧栏、队列和其他封面模型共用此实现。将数量上限提高到 1024，同时保持 64 MiB 像素预算；重复到达或晚到的小图不会再触发无效界面更新。高清大图尺寸与后台解码并发限制保持原有配置。

同一真实 API 响应在 Vulkan / Wayland / debug / 1435×1000 窗口中重放，使用同一份已经预热的磁盘缓存。每轮 230 次、每次 122px，依次下滚、上滚、再下滚，目标定时器间隔 16ms：

| 指标 | 修改前中位数 / P95 | 修改后中位数 / P95 |
| --- | --- | --- |
| 首次下滚输入处理 | 9.68 / 51.37 ms | 6.49 / 15.17 ms |
| 回滚输入处理 | 6.15 / 45.76 ms | 5.86 / 7.43 ms |
| 再次下滚输入处理 | 6.56 / 45.08 ms | 6.33 / 8.23 ms |
| 首次下滚事件循环间隔 | 42.44 / 80.97 ms | 23.07 / 35.41 ms |
| 回滚事件循环间隔 | 21.64 / 51.07 ms | 20.68 / 23.17 ms |
| 封面提交与请求处理 | 0.28 / 1.07 ms | 0.03 / 0.23 ms |

三轮封面交付总数从 601 降至 376，发生重复交付的 URL/尺寸组合从 226 降至 7（含歌单大图和创建者头像）。关闭封面加载的对照中，首次下滚输入 P95 为 8.19ms，支持封面变更导致重算的定位。

另用完整 `ApplicationRuntime` 在线恢复登录、打开歌单并滚动，最后回到首页拖动推荐列表。最终验证的首次下滚 / 回滚 / 再次下滚输入 P95 为 12.13 / 7.28 / 7.98ms；首页拖动输入 P95 为 0.84ms。打开歌单至曲目就绪仍约 2.28 秒，与详情 API 等待一致。事件循环间隔仍有超过 16.7ms 的样本；这些数字不是 GPU 帧时间，也不表示始终达到 60 FPS。

手动复测（显式读取现有登录会话，需要真实桌面、网络与单独的缓存副本）：

```sh
NCM_PROFILE_LIVE_PLAYLIST=主歌单 NCM_PROFILE_CACHE=/tmp/ncm-main-live-cache \
  timeout 115s cargo test --locked --offline profile_logged_in_playlist_runtime -- --ignored --nocapture --test-threads=1
```

也可以通过 `NCM_PROFILE_PLAYLIST_JSON` 和 `NCM_PROFILE_CACHE` 运行 `profile_api_playlist_scrolling` 重放私有响应；JSON 格式为 `{ "kind": "playlist", "id": "...", "body": <playlist_detail 的 body> }`。可加 `NCM_PROFILE_NO_COVERS=1` 做对照。不要提交私有响应；正常自动测试不读取账号、不访问音乐 API。

## 真实窗口滚动

2026-11-08，在实际 Wayland 桌面、Winit/FemtoVG OpenGL 后端上测量。机器使用 NVIDIA RTX 3060 Laptop GPU（驱动 615.78.08），构建为 Cargo debug，窗口为 1435×1000、缩放为 1。测试创建 10,000 首模拟歌曲，前 500 首各有一张预先加载的 128×128 封面；不启动 API，不读取真实账号。预热 2 秒后，以 16 ms 定时器发送约 120 次滚轮事件，每次向下 62px，完成后自动关闭窗口。

| 指标 | 修改前中位数 / P95 | 修改后中位数 / P95 |
| --- | --- | --- |
| 滚轮事件处理 | 52.53 / 72.17 ms | 4.14 / 5.92 ms |
| 渲染通知区间 | 56.02 / 78.13 ms | 10.39 / 14.39 ms |
| 事件循环定时器间隔 | 54.62 / 111.20 ms | 17.35 / 24.35 ms |

修改前，虚拟列表按可见行数创建控件，跨越行边界时会销毁或重建行；每一行的数据都直接依赖 `first-row + offset`，滚动会让整屏歌曲重新绑定。实际窗口调用栈中反复出现行布局、文字测量/整形，以及 OpenGL 纹理删除和驱动调用。此前封面提交优化没有解决这条路径。

现在 `VirtualRows` 按窗口高度保留固定数量的行控件，循环复用离开视口的行，只给新进入视口的行更换歌曲索引。另通过 `changed target-index` 在索引实际改变时写入行的 `item-index`，隔离滚动位置对行内容绑定的反复失效；仅把行索引改成循环计算仍会触发这些计算，实测滚轮处理仍约 35.6 ms。行内容继续绑定模型，因此封面、标题和收藏状态的后续更新仍然生效。歌单、专辑、喜欢的音乐、本地音乐、搜索、侧栏歌单和添加到歌单菜单均使用这一方式。

渲染数据测量 `BeforeRendering` 到 `AfterRendering` 的区间，不能等同于 GPU 显示完成时间，也不保证真实账号下始终达到 60 FPS。测试特意排除了网络等待和封面解码，以复现已有列表的滚动开销。先前无法连接 Wayland 是沙箱访问限制，本次获准连接桌面后已完成真实窗口测量。

复测（在 `slint-ui` 目录，需要可访问 Wayland/X11 桌面，单独运行）：

```sh
timeout 45s cargo test --locked --offline profile_real_playlist_scrolling -- --ignored --nocapture --test-threads=1
```

自动回归在五种歌曲页面中统计模型读取次数：微小滚动或跨越一行时最多读取三行，避免重新绑定整个视口；同时验证复用行的点击和模型内容更新。既有测试还覆盖大幅跳转、列表首尾、模型缩短、侧栏/弹窗/待播清单，以及封面请求范围。

## 封面提交

2026-11-08，在离线测试后端中复现大量歌曲的封面到达与滚动。使用模拟数据，不读取真实账号。构建模式为 Cargo debug，窗口为 1435×1000；每轮接收 4 张封面，共 16 轮。

| 歌曲数量 | 修改前单批封面更新中位数 | 修改后单批封面更新中位数 |
| --- | --- | --- |
| 100 | 0.18 ms | 0.12 ms |
| 1,000 | 13.49 ms | 0.39 ms |
| 10,000 | 19.83 ms | 0.59 ms |

修改前，`View::refresh_images` 遍历全部列表；每张小封面也使用 800 像素图片，内存中的图片和模型引用持续累积。修改后，封面 URL 对应实体 ID，模型通过 ID 索引定位需要更新的行；小封面使用 128 像素缩略图，大图按需升级至 800 像素。解码图片缓存限制为 256 张、64 MiB；淘汰同时更新模型以释放图片引用。

以上数据只衡量界面线程提交封面的耗时，不代表真实窗口帧率。该环境的软件截图整帧仍约 350–370 ms，包含为截图创建新缓冲区后的全屏重绘及 RGBA 转换，不能用作真实桌面滚动帧耗时。歌单首次解析和构建模型仍在主线程执行，一万首的模拟数据约 80–100 ms；这里针对用户确认的「列表出现后滚动/封面加载卡顿」路径。真实窗口的独立测量见上文。

复测（在 `slint-ui` 目录）：

```sh
cargo test --locked --offline profile_playlist_cover_updates_and_scrolling -- --ignored --nocapture --test-threads=1
```

自动回归还验证：一万行模型更新单个封面只访问匹配行（包括重复 ID）；小列表只请求 128 像素封面；缓存淘汰释放模型引用；滚回旧位置重新请求；晚到的缩略图不会覆盖已经加载的大图。
